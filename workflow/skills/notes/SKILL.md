# notes · 接口导读

为规范数据补充接口说明，帮助读者理解用途、已观测行为与适用范围。定义和录制样例是说明的依据。

## 输入与范围

阅读 [共享契约](../references/contracts.md)，确认用户或 pipeline 指定的接口。逐个读取 definition、引用的 examples 和已有 notes，必要时参考 `glossary.json` 与 `collection.json`。编辑范围为本次涉及的 `apis/<host>/<static path>/notes.md`；规范 JSON 的变更交由 classify 或 drift 处理。

## 写作步骤

1. 对照 endpoint、auth、request 与 responses，确保每项说明可追溯到定义或样例。缺少 example 时注明「尚无录制样例支持」；定义与样例不一致时记录差异，交由 classify 或 drift 处理。
2. 用简短中文说明用途、关键参数、鉴权与成功响应。围绕读者需要补充解释，避免重复完整参数表、JSON 或响应类型树。
3. 简述各失败变体的语义和观测码。结合业务语义解释成功或失败；同一语义对应不同 HTTP 状态时注明该关系。
4. 明确数据的含义：参数 `default` 表示样例观测值；`schema: null` 表示无法确定可信 body 结构，不保证响应为空；`{{NAME}}` / `<redacted:...>` 表示脱敏内容，不是可用凭证。
5. 保留仍准确的上下文，仅修正过时或受本次变更影响的说明。参数必填性、登录要求、限流、重试策略和线上可用性缺少证据时，注明未知；单次成功不能证明服务保证。

## 输出形态

按接口复杂度组织简短段落，说明用途、调用与鉴权、响应行为及必要的注意事项。变体较多时可使用列表；没有相关证据的内容可以省略。格式遵循共享契约。

例如有 `not-found` 的两种观测时，可写：「目标不存在时可见 HTTP 200 + code 1004，也可见 HTTP 404 且无业务码；两者在本接口归为 not-found。业务失败不能仅凭 HTTP 状态判断。」只在实际 examples 支持时使用该表述。

## 检查与交接

复核事实与修改范围，列出变更接口及待核实问题。仅修改说明文字时无需重复运行规范 JSON 校验；pipeline 在后续 render 时同步生成文档。独立任务要求同步生成物时，调用 CLI render。

notes 为可选输出。资料不足时仅说明已知内容，或跳过并记录原因；其余有效的导入步骤可以继续。
